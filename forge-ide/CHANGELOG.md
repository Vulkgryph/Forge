## [Unreleased]

## [0.3.0] — 2026-08-27

### Fixed

- **Making *Skip All Permissions* the default took one unconfirmed click.** In Settings it was a bare `selectable_label` that wrote the setting and saved it, and that setting arms every agent tab that does not exist yet — including remote ones, where a session started under it launches the agent with `--dangerously-allow-all` on a machine that may not be the user's. Switching a single live tab already asked for confirmation; the setting deciding for tabs in advance asked for nothing. It now opens a typed confirmation: the button stays disabled until you type `confirm`, with the consequence spelled out above the field, and Cancel leaves the default where it was. The word is a real function shared with its test, so the rule cannot drift from what the pane enforces.

- **The pty daemon's socket took whatever permissions the umask gave it.** Anything that connects to `~/Library/Application Support/forge-ide/ptyhost.sock` can create a pty, which is code execution as its owner. `bind` leaves the mode to the umask: 0755 under the usual 022, which is safe only incidentally — connecting requires the write bit, and that one happens to be the owner's alone. Under a umask of 000 the same bind yields 0777 and hands execution to every local user on the machine. `SECURITY.md` describes the daemon as "reachable by any process running as that user", and that is now true by construction rather than by luck: the mode is set to 0600 explicitly, and a failure to set it refuses to serve, because an unreachable daemon is a broken editor while a world-writable one is a privilege-escalation path. The test binds through the real code path under a deliberately permissive umask, so deleting the line fails it.

- **Nothing said the application bundle is ad-hoc signed.** `package_macos.sh` uses a Developer ID when one is in the keychain and falls back to `codesign --sign -`, and neither is notarized — so a bundle someone else built is refused on first open with a message about an unverified developer. Now documented, with the two ways past it and the honest alternative of building from source. Also: the SSH Remote feature bullet said the daemon "auto-uploads itself" without ever saying it *runs* there, which read as a convenience rather than as software landing on someone's server.

- **The model tunnel to a remote agent served whoever connected to it.** When this machine lends its model endpoints to an agent running on a remote host, SSH forwards a port on that host's loopback back here and Forge adds the API credential on this side — so the key never lands on that machine, which was the point. What the tunnel did not do was check who was calling. Loopback sounds private and is not: every process and every other local user on that host can reach it, and since the credential is attached here, anything over there could spend the user's tokens through their own proxy while holding no key of its own. Shared employer and client machines are exactly the documented use case. Each session now issues a 32-byte random token, hands it to the remote agent as the api_key of every endpoint it is lent — so the agent presents it on every request without needing to know it is authenticating — and the proxy answers `401` to anything that does not present it, before the request reaches a provider or a credential. The token authorises the tunnel and nothing else, is marked ephemeral so the agent never writes it to that machine's config, and dies with the session. The two existing proxy tests sent no credential and passed, which is what the old behaviour was; they now carry the token, and a new test refuses an unauthenticated request with nothing listening upstream, so a regression fails rather than quietly reaching a live endpoint.

- **`NOTICE` said the application bundle contained no third-party binaries. Four fonts are compiled into it.** `egui`'s default font set — Hack, Noto Emoji, Ubuntu and emoji-icon-font — is `include_bytes!`-ed through `epaint_default_fonts`, and `setup_fonts` keeps it as the fallback for characters the system fonts do not cover, so those files ship inside `forge-ide` whether or not they are the fonts you see. `strings` finds nothing because TTF name tables are UTF-16BE, which is presumably how the claim survived; comparing raw bytes finds all four. Three of the licences (SIL Open Font License 1.1, Ubuntu Font Licence 1.0, and the Bitstream Vera License that Hack carries) condition redistribution on the notice travelling with the font, so the texts are now in `licenses/` and `NOTICE` itemises each font, its copyright, and its terms. The same section now also names what a licence scanner will otherwise find on its own: four MPL-2.0 crates and where to get their source, vendored libgit2 under GPL-2.0 *with* the linking exception that makes it a non-issue, static OpenSSL, `webpki-roots`, and the Unicode-3.0 ICU data. A test asserts the attribution holds as long as the fonts are in the dependency graph — the obligation follows the dependency, and nothing else in the build would notice it changing.

- **The agent panel's top bar wrapped onto a second row at the width the panel opens at.** It carried six things, two of them wide — the context strategy and the network state — and both are settings you touch occasionally rather than facts you read while working, so they moved into a `⋯` menu on the row's right. What stays is what you actually watch: model, permissions, reasoning, context usage. As the panel narrows the row gives things up in order of how little they cost: the `·` separators first, then long labels for short ones (`Dangerously skip all` → `Skip All`, `Reasoning: High` → `High`, `42% ctx` → `42%`), then the disclosure triangles — a badge still highlights and still opens its menu without one. Nothing is dropped at any width, down to the 240pt the splitter's floor allows. Offline is the one exception to living in the menu: it changes what the agent can do, so it stays in the row, while online says nothing and does not. The thresholds are no longer guesses — a test lays the real labels out in the real font and sweeps every panel width from 240 to 800pt, which is what caught that a long model id (`claude-opus-4-6-20260501`, or a local `qwen3-coder-30b-a3b` tag) wrapped the row on its own in four separate bands. The model name now has an explicit character budget per width, and sheds its vendor prefix before it sheds anything informative.

- **A window restarted onto a *new* build came back without its remote connection, its geometry, or its identity; restarted onto the same build it came back fine.** Everything a restart needs is read from the window record, and reading it was all-or-nothing in two ways. `remote_host` was a host's name for a few builds and is the whole connection now, so a file from either side of that change failed to parse — and `serde_json::from_str::<Vec<_>>` gives up on the entire file at the first entry it dislikes, so one record from a different build erased every window's state. Silently, because the error was discarded. Records are now read one at a time, an entry that will not parse strictly is read field by field, and `remote_host` accepts either shape — a bare name becomes a host with just its name, which is enough, since the lookup on the way in matches by name against the SSH config. A field from a future build is ignored rather than fatal.

First public release. Everything below shipped in it; the version was written up
before it was tagged, and a further week of work landed on top of it, so the two
are one entry rather than a release nobody could install and a sequel to it.

### Changed (you can see what the agent is doing, and for how long)

- **A running tool call was a static dot.** Colour alone carried "running" versus "finished", so a call thirty seconds in looked exactly like a stale icon and there was no way to tell a working agent from a stuck one. The dot on a running call now breathes, with a halo that grows and fades with it so it reads as motion at a glance rather than only as a colour change. It is on the card that is executing — where the eye already is — not only on the status line above the input box. No extra wakeups: the panel already repaints on a 50ms cadence while a turn is live and not at all when it is not, and the animation asks for exactly that cadence rather than the next frame the loop will give it.
- **The status line said "Running shell_exec…"**, which says a tool is running and nothing about which one or why it might be slow. It now says what is being done to what — "Running cargo build --release", "Editing cascor.rs…", "Waiting on the explore subagent…" — from arguments it already had. Long commands are cut to one line here rather than wrapped, since this row sits directly above the input box and a wrapped command would push the box down the screen.
- **And it shows how long the current step has been going**, after two seconds, so the ones that finish quickly stay quiet. A model call and a five-minute `sleep` were previously indistinguishable — both were "working", and neither told you whether to keep waiting.
- **A command that says how long it will take now gets a countdown.** `sleep 300` becomes "~4m 19s left", read out of the command the agent already wrote — POSIX `sleep` with GNU's `s`/`m`/`h`/`d` suffixes, GNU `timeout`, Windows `timeout /t`, and PowerShell `Start-Sleep`. A `timeout` is shown as a ceiling ("up to 4m left") rather than a promise, since it may well come in under. Sequential parts add up, and a limit beats the sleep it wraps: `timeout 60 sleep 300` is a minute, not six.
- Both ways the estimate can be wrong fail quietly. If the command **finishes early**, the countdown goes with the step that made the claim — no timer left running against a command that is already done, and the next step never inherits the last one's estimate. If it **outlives the estimate**, the countdown disappears rather than sitting at zero or counting into the negative; the elapsed time carries on, which is the only honest thing left to say. And a command that merely *mentions* a sleep — `grep -E 'sleep 300' log` — is not one: parsing is quote-aware and only reads command position, because the alternative reports five minutes for a command that returns instantly.

### Fixed (the connected-host badge spilled out of its own box)

- **The status bar's SSH badge was a fixed 36pt slot with the host name painted centred inside it**, so any name of real length hung out of both sides — clipped by the window's left edge and drawn over the label to its right, which is what made the bottom-left corner unreadable. The badge sizes itself to its text now, and paints left-aligned inside its own box so it cannot grow leftwards off the window.
- **And the name is capped at 14 characters with an ellipsis**, so "sizes itself" cannot mean "grows without end" — `Admin-1-Tailscale` becomes `Admin-1-Tails…`. Counted in characters rather than bytes: a host can be called anything, and slicing a name mid-character is a panic rather than a cosmetic bug.

### Changed (a reconnecting window no longer looks like a brand new one)

- **Starting a remote session from a window with no local folder is the ordinary way in** — you open the IDE and connect from whatever is already there — so a restarted remote window has no folder to show. While the connection is being remade it showed "No folder opened" and an Open Folder button, which is indistinguishable from a window that has just been created. It now says which host it is reconnecting to, where the folder would be.
- And if the reconnect fails, the window says so in the same place, with a Try again button, instead of leaving the explanation in the OUTPUT panel and a window that looks fresh.

### Added (a restarted window says what it restored)

- **Every reason a remote window came back local was invisible from inside the window it happened to**, which is how the same report came back three times. A window now writes what was decided about it before it existed into its OUTPUT panel: that it is reconnecting to a host and which one; that its record named a remote but held no connection to remake; or that there was no record for it at all, so it came back with its folder and nothing else — which is what "it opened a fresh window" looks like from the outside.
- There is also a live test of the recording path, run against a host from the SSH config, because a restart *should* reconnect was claimed twice and was wrong both times — each time because something upstream had never written the connection down. It is skipped when the host is not answering, and only ever tries the one it is meant for: connecting is not a read-only act, since it uploads `forge-server` when the remote's copy is out of date.

### Fixed (three reasons a restarted window came back wrong)

- **Connecting to a remote was never written down.** The record is written immediately for a deliberate act — opening a folder, opening or closing a window — and waits out a settle timer for geometry, which changes continuously while a window is dragged. Connecting changed only the host, which read as geometry, so it waited; and the timer is only looked at again when a *window* event arrives, which connecting is not. So the connection never reached disk and a restart had nothing to reconnect to. Connecting, disconnecting and changing the remote folder are now deliberate acts too.
- **The record kept only the host's *name*.** That was the tidier idea — user, port and key live in the SSH config, so a copy is a copy to go stale — but it only works for a window connected to a *named* host, and a connection typed in by hand has no name. Those recorded nothing and came back local, silently, in exactly the case the user cannot fix by editing a config file. The whole connection is recorded now, still refreshed from the config when the name matches something there so a changed key path or port is picked up. Nothing secret is involved: it is the path to a key, not a key, and the same information the SSH config holds in plain text.
- **One window could be named by two records**, so a restart reopened it twice — and the older of the two carries older geometry, which is how a window came back the wrong size. A window keeps its id across a restart while the process it came from may have died without deregistering, leaving its entry behind on purpose so a crash does not lose the window. The newest entry for an id now wins. Records written before windows had ids carry `0`, which is not an identity — every one of those is a different window, and treating them as one collapsed three remembered windows into one.

### Fixed (a remote window restarted into a new process came back local)

- **A restart now names its windows by id**, so each comes back from its own record — with its geometry and, if it had one, its remote connection. Passing folders could not do that: the record is shared with every Forge process, so with more than one — now the normal case — the recorded set and the folder list differ, the folder list wins, and a folder is all a folder can say. That is why a remote window still came back local *after* the record learned to carry a host. Folders are still passed as the fallback for a record that cannot be read at all, where opening on the right workspace beats not opening.

- **The soft reload reconnects; a process restart could not**, because a connection cannot travel through an argument list and the window record did not carry one. The record now keeps the host's *name* and the folder that was open on it. Everything else about the host — user, port, key — is read back from the SSH config, where it is already kept once, so there is no second copy to go stale. A host that has since been renamed or removed opens the window locally instead: guessing at a connection is worse than not making one.
- The record's comment said this could not be done, because the app tracked a *pending* SSH host rather than an established one and could not be asked where a window was. That stopped being true when the connection started carrying its own host.

### Changed (a Window menu, and all of it typeable)

- **The window and restart commands moved out of File into a new Window menu.** They had collected at the bottom of File because that is where the first one went, and File is for documents — every one of these acts on a window or on the process behind it, which is what a Window menu is for, and it is where a macOS user looks for New Window anyway. New Window moved with them; the build line is now a footer at the bottom of that menu rather than sitting in the middle of the actions.
- **Not behind a "Developer" submenu**, which is where VS Code keeps its reload. With a build rolled out one window at a time these are the ordinary controls of a normal day, not diagnostics.
- **And all of them are in the command palette**, which is VS Code's actual answer and the only place it offers a reload at all. A command reachable only by hunting through menus is one you have to remember by position.

### Added (Window → Collect All Windows Into One Process)

- **Rolling a build out window by window leaves a process per window, and macOS gives every instance of an app its own Dock tile** — so three projects rolled out one at a time is three Forge icons, and the pinned one goes dark once the instance it was associated with has been replaced. That is inherent to running several processes, not a bug to fix, but there was no way back from it. This is the way back: when the rollout is done, every window is collected into a single process again, and the Dock returns to one icon. The window list comes from the record, which knows every process's windows, rather than from the process running the command, which only knows its own.

### Fixed (the remote terminal stayed put when the workspace moved)

- **Opening a folder on the remote left the shell wherever it was**, so the workspace and the prompt disagreed and the first thing you did in a new folder was `cd` into it by hand. Opening a folder locally has always restarted every local shell in it; the remote shell was simply never told. It now follows.
- Sent as a `cd` rather than by reopening the shell. A local shell starts in a fraction of a second, so restarting it costs nothing; a remote one may have a build running in it, and its scrollback is a session that took a round trip per keystroke to produce. `cd` keeps both, and if the shell is busy the line waits in the pty and runs when the prompt returns — exactly what typing it would have done. The path is quoted whether it needs it or not, with the tilde left outside the quotes so the shell still expands it.
- **Open in Terminal** is on the remote context menu too, for sending the shell somewhere without moving the workspace there — another thing the local tree has always had.

### Added (the remote explorer answers a right-click, and can make a folder)

- **Right-clicking a remote file or folder did nothing.** The local tree has had a context menu since it was written; the remote one never got one, which is backwards — a remote workspace is where you are least able to fall back on Finder. Rows now offer New Folder…, Copy Path, Refresh, and Open This Folder on a directory. The empty space below the rows has the same menu, since "a new folder *here*" is a thing to ask when no row means here.
- **New Folder… on the remote**, via a new `fs/mkdir` on `forge-server`. It creates parents, so `one/two/three` typed into the box is one request rather than three, and refuses when something is already there rather than reporting success for a folder it did not create — `create_dir_all` is happy to do nothing, which would make a typo look like it worked. `forge-server` is version-bumped so an already-connected remote replaces its copy instead of answering "unknown method".
- **The folder chooser takes a typed path**, with Go and Enter. Clicking down through a tree is fine when you are looking for a folder and hopeless when you already know where it is — which, on a remote box, is usually the case, from a terminal in the next panel. The box follows the listing as you navigate, so it always reads as where you are, and going somewhere typed is confirmed by the listing that comes back rather than accepted blind. There is a New Folder… button beside it, for making the folder you are about to open.

### Fixed (a gap between the end of the remote prompt and the cursor)

- **The remote terminal placed its cursor at `column × the font's advance for a space`, while the text beside it was placed by the galley.** egui snaps a glyph's advance when it lays a line out, so those two disagree by a fraction of a pixel per character: invisible at one character, and about three quarters of a character by the end of `sysadmin@spark-9f0d:~/Biophysical_NN$ ` — 9.2px at 13pt, measured. At 14pt the same error runs the other way and the cursor sits *inside* the text.
- The local terminal already measured a column by laying out a run of characters and dividing, which is right. There are now not two measurements: one function, used by both, so the cursor, the column count and the text cannot hold different opinions about where column *n* is. The column count was wrong by the same fraction, which is also what decided how many columns the remote shell was told it had.

### Fixed (a remote terminal opened showing nothing, scrolled to the bottom of its own blank space)

- **Making the grid shorter scrolled the top away regardless of what was on it.** A remote terminal's grid opens taller than the panel it is drawn in; the shell prints its prompt at the top; the grid is then fitted to the panel — and that fit pushed the prompt into scrollback, leaving a viewport of nothing. The terminal appeared black and you had to scroll up to find your own shell. Shrinking now gives up the empty rows below the cursor first, and only scrolls the top away when there is real content in the way, which is what keeps the cursor in view. A blank row a program painted a background onto counts as content — a highlighted band with no text in it was drawn deliberately.
- **The first fit no longer waits out the 400ms resize debounce.** That delay is there so dragging the splitter does not send a round trip per frame; the initial fit is not a drag, and waiting to correct a size the grid only guessed meant 400ms of showing the wrong thing.

### Fixed (the pty host served one client at a time, which multi-process Forge broke)

- **The daemon accepted one connection and then blocked until that client went away.** That was invisible while Forge IDE was a single process — its windows share one connection — and became a real fault the moment a window could restart into a process of its own: the second process's connection sat unaccepted in the backlog until its handshake timed out, at which point it concluded the daemon was wedged, took the socket away and started another one. The sessions recorded against the first daemon were then unreachable, so terminals stopped surviving a restart. It now serves each client on its own thread.
- **A session's output went to whichever client connected most recently**, because every push wrote into one shared writer. Correct only while "most recent" also meant "the only one". Each session now names its subscriber, set when it is opened and moved by a new `pty/subscribe` when a client reattaches after its own process restarted — which is what `PtyHostClient::reattach` had always needed to say and never did.
- Both are covered by tests that run the daemon and drive real clients against it. Restoring the serial accept fails them, which is how they were checked.

### Added (Restart All Windows reaches every Forge process)

- **"All windows" could only ever mean "the windows in this process".** Once windows have been moved out one at a time, "all of them" spans processes with no way to talk to each other — except that every one of them is already connected to the pty host, so it now carries the message. `File → Restart All Windows` asks the others to restart and then restarts this one. It reaches an idle window, which a flag on disk would not, and it reports how many processes it actually reached rather than claiming to have told everyone: an older daemon does not know how to pass the message on, and a process that has never opened a terminal is not connected to hear it.
- There is one such command, not two. It briefly shipped alongside a process-scoped restart, and the names — "All Windows" against "Every Window" — carried none of the difference between them. An "all" that quietly means "some" is a trap, and which process a window happens to live in is not something anyone should have to think about to pick a menu item. When the message cannot reach the other processes, the command says so and does what it can.

### Added (installing an update now says so, and offers both ways to take it)

- **Installing a new build cannot change a running window** — the process is already up — and nothing said so, which left the state where you install an update, see no change, and cannot tell whether it worked. A window now notices when the binary on disk is newer than the one it started from, and says so in a banner: what it is currently running, `Restart this window`, `Restart all windows`, and — stated outright, because it is the part nobody would guess — that one window at a time is fine and the others keep running. Also noted in the File menu, so a window can be asked at any time whether it is behind.
- **Window → Restart All Windows** brings everything up to date at once, for when the piecemeal rollout is finished with — every window, in every Forge process. Deliberately not on a keyboard chord: it takes every window down together, which is a thing to choose from a menu or approve from the banner, not to reach by mistyping the per-window shortcut.
- The check is throttled to once every fifteen seconds and only runs while a window is drawing, because it is a filesystem call — a notice arriving a few seconds late costs nothing, a `stat` per frame is not free.

### Fixed (rolling a new build out one window at a time lost windows, and you could not tell which was which)

- **The window record is one file, and whichever process wrote last erased the others' windows.** With three projects in three windows and one of them restarted onto a new build, that is two processes writing the same file — so the record stopped describing what was open, and the next launch came back missing windows. Each entry now records which process has it: a process replaces its own entries and keeps everyone else's. A process that closes its last window deregisters instead of erasing the others, and one that dies without deregistering keeps its windows for as long as their saved sessions live, so a crash does not cost you a window while a long-dead process does not resurrect one forever. Entries written before this carry no owner and are replaced as they always were, which is correct — there was one process then.
- **Every window now says which build it is running**, in the OUTPUT panel as it opens and in the File menu: `Forge IDE 0.3.0 · Aug 21 23:16`. The version alone cannot distinguish two builds of the same version, which is exactly the case while a build is being rolled out window by window — all of them say `0.3.0` and none says which one. The stamp comes from the binary the process actually started from, so replacing that file on disk does not change what a running window reports.

### Added (Window → Restart This Window — a hard restart of one window)

- **There are two useful meanings of "reboot this window" and only one of them existed.** `Reload Window` rebuilds a window's state inside the process it is already in: fast, keeps everything, and cannot replace the process — so it cannot pick up a newly built binary, cannot clear anything the process itself is holding, and gives a suspicious user nothing to see because there is nothing to see. `Restart This Window` hands the window to a genuinely new process — new PID, current binary on disk — and closes it here. Every other window carries on in the old process, which is the part `Restart Forge (All Windows)` cannot offer.
- This needs no per-window-process architecture. Windows start in whatever process opened them and a restart *migrates* one out, so the topology ends up being whatever you have restarted rather than something chosen up front. Geometry comes from the window record, as it does for any reload, and the folder is passed alongside so the window still opens on the right workspace if no record can be read. Terminals survive it: they belong to the pty daemon, and the new process reattaches to them by id.
- The new process is spawned *before* the old window is closed, so a failure to start one leaves the window where it was rather than closing it with nothing to replace it.

### Added (a reloaded remote window reconnects itself)

- **"Reload Window" on a remote workspace now makes the connection again, and the agent tabs carry on where they were** — resuming the session on that machine, which is still there, so the conversation genuinely continues rather than starting over next to a transcript of the old one. Key-based hosts reconnect without asking. A host that wants a password cannot be reconnected silently, since the password is never stored, and falls back to local with the transcript marked.
- While the connection is being made, a tab holds its transcript and starts **no process at all**. A local agent started in that gap would be on the wrong machine and would try to resume a session that is on the other one. Anything typed in the meantime is held — in the box or already sent — and goes out once there is something to send it to, rather than being written into a session with no agent behind it and leaving the tab looking like it is thinking about it.
- The window also restores its own state while reconnecting, which it previously refused to do while connecting anywhere. That refusal is right for a window *opening* a remote workspace — it should not adopt another window's local files and terminals — and wrong for one reloading its own, whose terminals are the local pty daemon's and would otherwise be left running with nothing pointing at them. That was the reason this was not done sooner.
- **File → Restart Forge still comes back local**, because the new process is told which folders to open and nothing else.

### Fixed (a reloaded remote window came back local with the remote's transcript and no sign of it)

- **Neither reload can keep an SSH session** — the connection belongs to the app being dropped — so the window comes back local while the transcript comes back whole. Keeping it is right; you can still read what happened. But with no boundary in it, it read as one continuous conversation with the machine you are on, and it was not: the agent that produced it was on the remote, and its session log stayed there. The reload now writes the break into the transcript where it happened, naming the host, saying the session stayed with it, and saying that continuing below continues a different conversation. Written by the code that drops the connection, so it cannot land in the wrong place, and it does not stack if you reload twice.
- **It also stops trying to resume the remote's session.** That recovered — forge-agent reports the session as missing and the tab falls back to a fresh one — but it recovered from a spawn that could never have worked, and reported it as an error the reader then has to interpret. An id naming a log on a host we are no longer connected to is not a resumable session, so it is given up at the same moment the connection is.

### Changed (a subagent's work is now visibly a subagent's)

- **There was no way to tell, reading the transcript, which lines were the main agent's and which belonged to a subagent.** A delegated task rendered as a one-line marker saying "running — see below", with the actual work in a docked strip above the input box — the same subagent in two places, and its tool calls nowhere near the conversation they belonged to. A subagent now gets its own block in the transcript: a rule down the left edge, its name and live activity at the top, its tool calls inside, its answer at the bottom, collapsible. Inside the rule is the subagent's; outside it is the agent you are talking to. Nested subagents nest inside their parent's rule.
- **The docked strip now appears only for a subagent with an approval waiting.** That is the one thing the transcript cannot do on its own — an approval three screens up in the scroll is one nobody answers, and the turn stays blocked until they do. Otherwise it is absent rather than a second copy of the block.

### Fixed (a finished subagent could keep saying "running" for the rest of the session)

- **The card and its strip entry never cleared, because the finish landed on the wrong card.** Subagent ids are `sub_0`, `sub_1`, … from a counter that restarts at zero in a new process — and a transcript outlives the process: a resumed session, or a tab whose agent was respawned for a permission-mode change or a window reload, keeps its items and gets a second `sub_0`. The lookup searched oldest-first, found the *previous* `sub_0`, and marked it finished again; the live one never finished. It now searches newest-first, which is the only order a finish can mean.
- **And there was no mechanism to clear a card whose finish went missing at all** — a crashed agent or a dropped event pinned it forever. A parent turn cannot end while a subagent is live, since `delegate_task` blocks it, so anything still marked running when the turn ends, is cancelled, or loses its process is now closed out.
- **The block could not shrink below ~370pt**, which is how text ends up clipped at the panel's right edge: the live-activity label was laid out at its natural width, setting a minimum width for the row, then the block, then the whole transcript. It is now sized to the space left and truncated, and the block fits down to 220pt.

### Changed ("Reload Window" reloads a window, not the whole process)

- **`Ctrl+Shift+R` used to replace the entire process**, taking every other window's conversations, language servers and SSH connections down with it — for a reason that was almost always local to one window. It now rebuilds that window's app in place, keeping the OS window, the swapchain and the egui context. Teardown is by drop (the agent child and language servers are killed by their own `Drop`), and shells are untouched: they live in the pty daemon, so the rebuilt window reattaches to the same running ones by id. The window keeps its position and its files, and every other window keeps working.
- **The process restart is still there, as File → Restart Forge (All Windows).** Two things only it can do: pick up a newly built binary, and re-establish an SSH session — a reloaded remote window comes back local, because the connection belongs to the app being dropped. It is deliberately not on a keyboard chord; it is not a stronger reload, it is a different blast radius.
- Unsaved editor changes are not preserved across either one, unchanged from before — the session records which files were open, not their unsaved contents.

### Fixed (two dialogs browsed the Mac while the workspace was on a remote host)

- **"Open Folder" and "Go to File…" both listed the local filesystem regardless of where the workspace was.** On a remote session that is the wrong machine: the folder dialog offered Mac folders, and `Ctrl+P` offered Mac files — which, if one happened to be there under the same path, opens a *different file* than the one intended. Both now branch on whether the session is remote, and the local behaviour is unchanged. Quick Open names the host in its header, since the whole failure was not being able to tell which machine you were looking at, and a listing that is refused or times out says so rather than reporting an empty folder.
- **The remote workspace root was fixed at connect time** by the connection form's "Remote dir" field — the explorer could drill into a directory but the workspace never moved, so the agent kept its original root. Choosing a folder now moves it, restarting the agent there because its project root is fixed at spawn (it is `cd`-ed into the workspace when the process starts). The transcript carries across, as it does for a permission-mode change.

Which entries are shown, how directories are marked, what order rows come in and where the entry cap falls are now one implementation shared by both listings, so a remote workspace cannot quietly behave unlike a local one. The `fs/list` request itself is likewise one implementation, where the explorer, the folder chooser and Quick Open previously each hand-rolled it.

### Fixed (closing a window while others stayed open silently leaked GPU memory)

- **`EguiPass` (the descriptor pool, per-frame vertex/index buffers, and every uploaded texture for one window) had no `Drop` impl — only the shared, process-wide pipeline did.** Closing one window while others (and the process) stayed open just dropped the struct with nothing to release its actual Vulkan handles, so every window close leaked GPU memory for as long as the process kept running. Found while auditing an unused-but-correct `EguiPass::destroy()` method that already did the right teardown — it just wasn't being called. ### Fixed (an SSH config `Include` directive with a relative path resolved against the wrong directory)

### Fixed (the app would have failed to launch at all on any machine but this dev one — pre-release packaging work)

- **OpenSSL**: `git2`'s `https` feature dynamically linked the system's OpenSSL (confirmed via `otool -L`: `/opt/homebrew/opt/openssl@3/lib/libssl.3.dylib`) — anyone without that exact Homebrew package installed would get an immediate "library not loaded" crash on launch. On any other machine, every single candidate would fail and the app would refuse to start with "MoltenVK not found." Verified directly: built a real minimal `.app` bundle with MoltenVK in `Contents/Frameworks/`, hid the dev-checkout copy entirely, and launched the bundle from `/tmp` (unrelated to the dev checkout) — confirmed via `vmmap` that it loaded the bundled copy, not the (now-hidden) dev one.

### Fixed (click-drag to select text in the agent chat panel or a terminal just scrolled instead)

- **egui's `ScrollArea` defaults to `drag_to_scroll(true)` — a touch-screen-style pan gesture that claims a click-drag on its contents *before* the selectable text inside gets a chance to interpret the same drag as text selection.** On a desktop app driven by a mouse, that meant click-drag-to-select never actually worked anywhere text was shown inside a scroll area — it always panned the view instead. Disabled specifically on the areas that hold real selectable text: the main chat, a tool result's or terminal command's expanded output, and both the local and SSH terminal panels. Wheel/trackpad scrolling and the scrollbar itself are a separate input path and are unaffected — this only turns off the click-drag-to-pan gesture, which nothing on a desktop app actually needs it for.

### Fixed (the Source Control panel didn't notice forge auto-initializing git mid-session)

- **forge-agent now auto-initializes git for a project that doesn't have it (see forge's own changelog) — but Forge IDE's Source Control panel only ever checks for a repo once, at folder-open time, so it silently stayed in its "no repository" state for the rest of the session even after a real `.git` appeared.** Now recognizes forge's own notice for this and re-checks right when it happens, so the panel picks up the new repo immediately instead of needing a reload.

### Fixed (a long agent conversation made the whole app, including typing itself, feel laggy)

- **The conversation auto-save ran unconditionally on *every single frame*, not just when something had actually changed — cloning the entire item list, JSON-serializing it, and writing it to disk every repaint, including one triggered by typing a single character anywhere else in the UI.** Measured ~40ms/frame from this alone on a real 1442-item conversation. Fixed by only saving when the item count has actually changed since the last save; every other save point (tab switch, tab close, new tab, session-restore-on-reboot) already saves unconditionally, so nothing is lost — just not needlessly re-flushed every frame.
- **Separately, the chat view rebuilt and re-parsed the markdown for *every* item in a conversation's full history on every frame, with no caching (unlike the editor/terminal panels, which already cache their shaped output) and no limit on how far back it went.** By default now only the most recent 150 items are rendered, behind a "Show N earlier messages" banner for the rest — keeps a long-running conversation's per-frame cost roughly constant instead of growing with its length.
- **Combined, these dropped a real 1442-item conversation's per-frame render cost from ~85ms to ~6ms** (measured directly, not estimated) — easily enough on its own to explain both the general slowdown and the reported input lag, since every keystroke's repaint had to pay the full cost above before the new character could even appear.

### Fixed (some markdown tables silently rendered as a single garbled paragraph instead of a table)

- **`soft_wrap` (inserts an invisible zero-width space into any run of 40+ non-whitespace characters, so egui's word-wrap has a break point inside otherwise-unbroken long tokens like URLs) was being applied to the *entire* raw markdown text before any parsing happened, not to the individual pieces of text that actually get displayed.** A GFM table separator row (`|--------|----------|---------------|---------------------|`) is pure dashes and pipes with no whitespace at all — with 4+ columns it routinely exceeds 40 characters, so it reliably got a zero-width space spliced into the middle of a dash run. That broke the exact check that recognizes a separator row (every character must be `-` or `:`), so the table was never recognized as a table in the first place and fell back to rendering as one plain, garbled paragraph — looking exactly like the raw `| a | b |` syntax dumped as text. Fixed by moving where wrapping happens: the raw text is now parsed for structure first (headings, lists, code fences, and table rows/separators all see the pristine original text), and `soft_wrap` is applied individually to each piece of text right before it becomes a label — after parsing, not before. Verified by reproducing the exact reported table in a live instance (garbled before the fix, a proper grid after) and confirming code blocks and prose still wrap the same as before.

### Fixed (a freshly-submitted plan showed its approve/reject buttons but not its actual content)

- **The plan card's content lives in its own nested `ScrollArea` (capped at 280px tall) — but a plan almost always arrives as the newest chat item, meaning the outer chat pane (which auto-scrolls to the bottom) is already scrolled right to it, and `ui.available_height()` at that cursor position reflects only whatever sliver of the *viewport* is left below, not a sensible content height.** egui's `ScrollArea` only guarantees its default 64px minimum in that situation — nowhere close to enough to show even the plan's own heading, let alone the rest of it, while the buttons below it (not height-constrained) rendered completely normally. Fixed by giving the plan's scroll area an explicit `min_scrolled_height` (220px), so it's actually visible regardless of where the chat happens to be scrolled to. Found and confirmed via a real plan-mode run in a live instance, screenshotted before and after — same root cause class as this session's earlier "content squeezed to nothing by an unrelated layout constraint" bugs (the markdown table and queued-message width issues), just a height version instead of a width one.
- **The same construct — a nested, height-capped `ScrollArea` with no `min_scrolled_height`, embedded directly in the chat item flow — affected an expanded tool result's full output and an expanded terminal command's full output too, for the identical reason whenever either happens to be the newest item.** Fixed both the same way.

### Fixed (resuming a conversation after reboot gave the agent a fresh, empty context)

- **Reopening a saved conversation — after a reboot, from the history list, or on a permission-mode change that requires a fresh subprocess — only ever replayed the chat transcript into the *UI*; the actual `forge-agent` subprocess backing it was always a brand-new process with no memory of anything before.** It looked resumed (every prior message was right there on screen) but the model genuinely had no idea any of it had happened — forge-agent does support resuming its real conversation state via `--resume-session <id>`, Forge IDE just never captured or passed that id anywhere. Now captures forge's own session id from `init` and saves it alongside each conversation; reopening one passes it back via `--resume-session` so the subprocess reconstructs its actual prior history (verified directly against forge-agent: resuming reattaches to the exact same on-disk session log rather than starting a new one, and the model correctly recalls facts from before the "reboot" using only that restored history, no re-reading anything). Conversations saved before this fix don't have a stored id and fall back to the old UI-only replay, same as always.
- **Found while testing the above against a real conversation: if the saved session id's log was never actually written (a subprocess that got respawned but never received a first message before this fix existed, essentially anything predating it) or has since been deleted, `--resume-session` makes forge-agent report "Session not found" and exit immediately, before ever sending `init` — which left that tab permanently dead, showing one error and nothing else working.** Recognized specifically and handled by falling back to a fresh, non-resumed spawn automatically, with a plain status note instead of a scary error — the displayed transcript stays, the agent just genuinely doesn't remember it, same as before this whole fix.

### Fixed (every saved conversation showed up in every workspace, regardless of which folder it was from)

- **Conversation history was a single global list — `~/Library/Application Support/forge-ide/conversations/` — with nothing recording which folder a conversation belonged to, so opening the history panel in any workspace showed every conversation ever had in any workspace.** Each conversation now records the workspace folder it was created in, and the history list/session-restore only pull in ones matching the currently open folder. Conversations saved before this fix don't have a recorded folder and still show up everywhere, same as always, until they're next reopened and re-saved, at which point they get scoped to whichever folder that happens in. Also fixed a related gap this surfaced: the workspace folder was stored exactly as passed on the command line (e.g. a literal `.`), which would have made two different folders' conversations collide or the same folder's conversations split apart depending on how it was opened — it's now resolved to a stable absolute path first.

### Fixed (a queued message could widen the window to full width, permanently)

### Added (a queued message can now be sent immediately instead of waiting)

### Fixed (the app could burn significant CPU at complete idle, occasionally severely enough to look hung)

- **`about_to_wait` rendered every window unconditionally on every single invocation — but most invocations of it are *not* actually because our own requested `WaitUntil` deadline elapsed.** The OS/runloop calls it for all sorts of unrelated reasons far more often than that (measured ~100-120 calls/sec at complete idle on this machine, vs. the ~3/sec our own 300ms idle baseline alone asks for). Every one of those extra wakeups was doing a full egui layout pass plus a Vulkan submit, regardless of whether anything could possibly have changed — a real, measured ~15-30% of a CPU core burned at idle in a debug build, for nothing. `about_to_wait` now only does that work when a real window event happened since the last render, or its own previously-requested deadline has actually passed; a spurious early wakeup just re-asks for the same deadline and returns immediately. Confirmed via direct measurement: idle CPU dropped to ~0.2-0.4%, roughly two orders of magnitude down from before, with no change to input responsiveness (real events still always mark the next wakeup dirty, same guarantee as before). Two windows both idling doubled this waste, which is the likeliest explanation for a report of the app becoming completely unresponsive after opening a second window's agent panel — not a bug in the agent panel itself, which never reproduced in isolation, but the cumulative baseline cost tipping over into visible unresponsiveness under extra load.

### Added (password prompts from agent-run shell commands now have a real answer path)

- **A shell command blocked on stdin (a `sudo`/`ssh`/etc. password prompt, or any other interactive prompt) previously showed "Forge IDE can't send yet — start a new conversation" and permanently dead-ended the turn**, for both the foreground command and any backgrounded one — the wire protocol already supported answering both (`process_input`/`bg_process_input`), Forge IDE just never implemented sending them. ### Added (Esc now actually interrupts a running agent turn)

### Fixed (an agent conversation didn't come back after Reload Window unless its window happened to be the one that triggered the reload)

- **`reload_window()` unconditionally saves session state before reloading (bypassing the opt-in `restore_session` setting, since a reload is the same session continuing) — but only for the one window it was called on.** Since a reload tears down every open window, not just the triggering one, any other open window's conversation/open-files state never got saved at all before being swept away. Every window now gets that same unconditional save before any of them are torn down.

### Fixed ("Reload Window" only ever restored one window, even with several open)

- **`exec` replaces the entire process, not just the reloading window** — so a reload triggered from one window while others were open needed every open folder passed along, not just the triggering one; main.rs was fixed earlier to gather all of them. That turned out to be necessary but not sufficient: `exec`'s defining property — same PID, same process, no destructors run — also meant the *relaunched* process's own `resumed()` handler never got far enough to create more than its first window. No panic, no error; the run loop simply never called back again after that first window, in a way that reliably reproduced regardless of how long it was given. Best-supported explanation is that macOS AppKit ties significant state to a PID's first `NSApplication` registration, and a second one spun up in-place under a reused PID can't properly pump events for anything beyond it. Switched to spawning a genuinely new process (its own PID) and exiting the old one instead of `exec`-ing in place — confirmed this reliably restores every window that was open, not just the first, where `exec` never did regardless of wait time. The explicit GPU/window teardown added for the `exec` approach still runs unchanged before the handoff either way.

### Fixed (new files created by an agent in a fresh workspace never showed up in the file tree)

- **The file watcher only ever tried to reload matching *open* buffers on an external change** — a brand-new file an agent just created was never open in an editor tab to begin with, so nothing happened at all: no file-tree entry, no notification, nothing. The file tree now refreshes once whenever the watcher reports any change, not just when it matches something already open — most visible in a fresh, mostly-empty workspace where an agent is actively creating files from scratch.

### Added (plan review now has a real approve/reject card instead of a dead-end message)

### Fixed (opening a new window was very slow the first time, every time)

- **Every window built its own fresh Vulkan instance, logical device, and egui graphics pipeline from scratch** (`GfxContext`/`EguiPass`), with nothing shared across windows in the same process — the "first window slow, every one after instant" pattern people noticed was really "the *first* window created in *this run* is slow," which happened to look like a one-time cost because most sessions only ever open one window per launch. Split both into a process-wide shared part (Vulkan instance/device/queue, and the egui pipeline/layout/descriptor-set-layout — the objects whose creation triggers MoltenVK's expensive Metal shader compile) built once by the first window, plus a per-window part (surface, swapchain, framebuffers, command pool, sync objects, and the per-window egui textures/vertex-index buffers) that every window still creates for itself. A shared pipeline is valid across each window's own separately-created `vk::RenderPass` because Vulkan only requires render-pass *compatibility* (matching attachment format/sample count), not the same object — which holds here since every window picks its swapchain format against the same physical device. Every window after the first now genuinely skips instance/device/pipeline creation instead of just getting lucky on the OS's shader cache.
- **Two of the three "New Window" entry points (the File menu button and the Command Palette command) never actually used the fast, in-process path above at all** — they spawned a whole separate OS process via `Command::new(exe).spawn()`, which pays the full instance/device/pipeline cost from scratch every time regardless of the sharing fix. Only the raw `Ctrl+Shift+N` shortcut went through the shared path. All three now go through the same in-process window creation.
- **"Reload Window" called `exec` directly and synchronously from inside `draw()`** — `exec` replaces the process image without running any Rust destructors, so the old window's entire Vulkan/Metal/window-server state (instance, device, swapchain, surface, the actual macOS window) was never torn down, just abandoned for the OS to notice and reclaim on its own schedule instead of a clean handoff. The actual `exec` is now deferred to the winit event loop, which explicitly drops every window (running `GfxContext`'s real teardown) and the shared Vulkan context first.

### Fixed (tool calls under "Dangerously Skip All" rendered as permanently stuck "awaiting approval")

### Fixed (terminal panel dropped frames while a process was actively producing output)

- **The terminal's Galley cache (added earlier to fix idle CPU usage) was keyed on a version counter that bumps on *every* `process()` call — meaning it correctly skipped re-shaping while idle, but re-shaped the *entire* scrollback (thousands of lines on a long session) on every single update while a process was actively streaming output** (a build running, or Claude Code's own UI redrawing many times a second) — exactly when smooth rendering matters most. Fixed by caching the scrollback and the viewport as two separate Galleys: scrollback is immutable history (only changes when a line actually scrolls into it), so it's now keyed on its own `scrollback_version` that bumps far less often; the viewport (~50 rows, not thousands) is what actually re-shapes on every update, and it's cheap. Applied to both the local terminal and the SSH terminal.

### Fixed (a markdown table with substantial content in every column could force the chat panel stuck wide open)

- **`render_table`'s last-column width computation could exceed the panel's available width** — `(available - used).max(*last)` was meant to never let it shrink below its own natural size, but that also meant it could grow *past* the leftover space whenever the last column's natural content was wider than what was left, silently overflowing the panel. Once that happens, the chat's measured content width grows to match, which then feeds into the *next* table's own available-width measurement — a long, table-heavy conversation could snowball this into the agent panel stuck at (or near) full window width, unable to shrink back down. Fixed to hard-cap at the leftover space instead (accepting a narrower, more-wrapped last column over an overflow).

### Fixed (`shell_exec` output could show raw terminal escape-sequence garbage instead of the command's actual output)

### Fixed (full tool-call output was truncated to 200/400/600 characters)

### Fixed (terminal occasionally typed a stray "B" over whatever you'd just typed)

- **Root cause: our VT100 parser didn't recognize `ESC ( <c>` (designate G0 character set — e.g. `ESC ( B` for plain ASCII), a standard sequence Ink-based TUIs like Claude Code's CLI send after drawing a special glyph (its spinner) to switch back to normal text.** The parser treated `(` as an unrecognized second byte and reset to normal-text mode without consuming it, so the sequence's real final byte (`B`) landed as a literal typed character at the cursor — which is exactly where you'd just typed, making it look like your input got replaced. Diagnosed by temporarily logging raw PTY bytes in both directions and catching the exact `IN " " / OUT "\x1b(B\x0f"` pair. Fixed by properly consuming the 2-byte character-set-designation sequence instead of falling through the catch-all reset.

### Fixed (scrolling still felt rough, and CPU was still pegged, even after the idle-repaint fix)

- **Every frame rebuilt and re-shaped the terminal's *entire* scrollback from scratch — thousands of lines on a long-lived session — regardless of whether anything had actually changed since the last frame.** `Terminal::draw_sized` (and the SSH terminal's equivalent, `draw_ssh_terminal`) called `Grid::to_layout_job` unconditionally on every single render, then handed the result to egui's font layout, which re-shapes and re-measures every glyph. This alone dominated frame time badly enough to peg a full CPU core continuously and make scrolling feel rough anywhere in the app (not just in the terminal) — confirmed by profiling a real, already-running instance with `sample`: ~78% of all main-thread samples over a 3-second window were inside this exact call path, with the event loop essentially never actually reaching its idle sleep. An earlier attempt at fixing the roughness (adding a ~240Hz repaint tier while the user is actively interacting) didn't address this, since the bottleneck is the *cost* of each frame, not how often frames are scheduled. Fixed by caching the built `Galley` on `Terminal`/`IdeApp`, keyed by a cheap version counter bumped only when the grid's content actually changes (new PTY output, a resize, a session-restore) — a cache hit is just an `Arc` clone, skipping the rebuild and re-shaping entirely. This is the same "cache the fully-shaped output, not just the intermediate job" pattern already used for the main editor's syntax highlighting.
- **Scrolling/dragging also gets a modest smoothness assist**: while the user is actively touching the mouse/trackpad/keyboard, the app now renders at up to ~240Hz for 200ms after the last bit of input (instead of only the 50ms/300ms background-polling cadence), closing the small gap between "real input always wakes the event loop" and "the frame after that wake is actually cheap enough to keep up." Falls back to the normal cadence the moment interaction stops.

### Fixed (missing-glyph "tofu" boxes for common symbols in agent chat text)

- **Arrows (→ ←), checkmarks (✓), and similar common symbols in agent-generated text rendered as an empty box (□)** instead of the actual character — e.g. a heading like "Agent → UI" showed the arrow as a missing-glyph placeholder. Root cause: macOS's HelveticaNeue (this app's primary UI font) has no glyphs for these characters at all, and egui's own bundled default fonts — the only fallback in play — don't cover them either. Added a dedicated symbol-coverage fallback font (`Arial Unicode.ttf` on macOS, `seguisym.ttf`/DejaVuSans on Windows/Linux) right after the main UI font in `setup_fonts`, so ordinary text still renders with HelveticaNeue and only the glyphs it's missing fall through to the new one. Verified live: confirmed via `fontTools` that HelveticaNeue.ttc covers none of →/←/✓/⇄/▶ while Arial Unicode.ttf covers all of them, then confirmed with a temporary `egui::Context`-based unit test (checking `Fonts::has_glyph` after `setup_fonts`) that the app's real font setup now reports coverage for all three before removing the test.

### Fixed (agent chat: markdown tables — width and a real ID collision)

- **Table columns wrapped one word per line instead of using the available panel width**, and — more seriously — **two tables in different messages could crash the render with an egui "Second use of Grid ID" overlay.** Both were in `render_table` (`src/markdown.rs`): (1) `egui::Grid` sizes each column to its content, and a wrapping `Label` inside a cell has no way to tell the grid "give me more room" on its own, so a column's wrap width got stuck at whatever narrow guess the first layout pass made. Fixed by measuring each column's widest content up front and handing whatever space is left over to the last column. (2) The Grid's id was salted with a per-message sequential counter (`table_n`, reset to 0 at the start of each message's render) — reasonable-looking, but nothing guarantees two different messages' sibling `ui.vertical()` wrappers produce different ids from `Grid`'s point of view, so two messages each containing their own "table #1" could collide. Fixed by salting with the table's actual content (header + rows) instead — unique per distinct table regardless of how many others exist elsewhere in the conversation, and still stable frame-to-frame for the same table (immediate-mode rerenders every frame). Verified with a unit test confirming different content hashes to different ids while identical content stays stable, plus a live-`egui::Context` smoke test exercising the actual measure/`add_sized` layout path.

### Fixed (file tree: "New File…"/"New Folder…" silently did nothing at the workspace root)

- **Right-clicking empty space in the Explorer panel, or a top-level file, to create a new file/folder never actually created anything.** The inline name-entry box (typed name → Enter → `std::fs::File::create`) only ever rendered inside the loop that draws each tree row, gated on finding a row whose path matched the target directory — but the workspace root itself never has a row of its own in that list (only its *children* do), so whenever the target directory resolved to the root — the panel-background menu always targets it, and so does right-clicking any file directly under the root — no row ever matched, the input box never appeared, and the pending "creating" state was stuck with nothing to confirm or cancel it. Right-clicking a non-root folder happened to still work, just misplaced (the box rendered *above* the target folder's row instead of nested as its first child, since the check ran before that row was drawn). Fixed by extracting the shared render/commit logic into `FileTree::draw_create_row`, called once before the tree loop for the root case and once right after a folder's own row for the nested case — so root-level creation now works, and the box reads as VS Code's does (nested under the folder you right-clicked, not floating above it).

### Fixed (high idle CPU/energy usage)

- **The event loop no longer spins continuously.** `main.rs` set `ControlFlow::Poll`, which re-runs egui's full layout + tessellation + GPU frame submission as fast as the OS would schedule it, forever — even sitting completely idle with the window unfocused. Replaced with a demand-driven `ControlFlow::WaitUntil`/`Wait`, using `egui::Context::set_request_repaint_callback` to track the earliest time any window's frame actually asked to be woken again. Real input (typing, clicking, resizing) still wakes it immediately regardless — winit delivers those as actual OS events, independent of this.
- **Removed ~8 call sites that were forcing an immediate repaint every frame on a background channel's "nothing happened yet" branch** (SSH connect/PTY/file-open/directory, git tasks, `gh` availability check) — a leftover "keep polling" pattern that (combined with the `Poll` fix above) would have kept the loop busy-spinning even after moving to `Wait`. Replaced with one consolidated scheduler in `IdeApp::draw`: a 300ms baseline that always runs (catches anything not explicitly listed — a file-watcher event, a stray LSP response), plus a 50ms cadence while something's genuinely in flight (agent streaming, a background git/SSH/task/dialog result, or the anvil-heat cooldown animation still playing).
- **Terminal "activity" is now judged by actual recent PTY output, not merely whether the terminal panel is visible.** The Terminal panel is open by default, so the first pass at this fix — gating the fast 50ms tier on panel visibility — made that tier effectively *permanent*: a shell sitting idle at its own prompt, with nothing running, was still being repainted 20 times a second forever. Caught this by measuring a real, already-running (session-restored) instance rather than trusting a synthetic idle-workspace test — `top`/`ps` CPU-time deltas and a `sample` stack profile both showed the fix hadn't actually landed for real usage. `Terminal` now tracks `last_output: Arc<Mutex<Option<Instant>>>`, updated by the feeder thread(s) whenever new bytes are actually decoded (`recently_active(window)`); the SSH remote terminal gets the equivalent tracking in `IdeApp`. The fast tier now only engages while a terminal has produced output in roughly the last 2 seconds — an idle shell correctly falls back to the 300ms baseline almost immediately.

### Fixed (Reload Window: terminal screen contents didn't survive)

- **Reattached terminals now show what was actually on screen before Reload Window, instead of coming back blank.** The pty-host daemon keeps the underlying shell (and whatever it was running) alive across a reload, but Forge IDE's own in-memory terminal-emulator state (the `Grid` — what's actually visible right now) lived only in the process being replaced and was previously just discarded; reattaching only resumed the live byte stream going forward; a lone `Ctrl+L` redraw request papered over the common "shell sitting idle at its prompt" case but did nothing for a foreground program (a dev server printing logs, a REPL, an editor) that doesn't redraw itself on request. Session save now snapshots each terminal's visible viewport (cell contents + cursor position) **and its full scrollback history**, and restores both onto the fresh `Grid` before the reattached terminal's live feed even starts — the first pass at this only snapshotted the viewport (matching VS Code's own terminal restore), but that meant scrolling up after a reload hit a hard wall right where the visible screen ended, silently losing everything before it; scrollback is now carried across the same way. The `Ctrl+L` fallback now only fires when there's no snapshot to restore at all (first-ever reattach); sending it after a successful restore risked disturbing a foreground program that treats it as literal input rather than a redraw request (e.g. inserting a form-feed character into whatever's being typed in `vim`) instead of just refreshing a shell prompt.

The file tree and agent panel toggle independently under the hood (`file_tree_full_height` / `agent_panel_full_height`), implemented by choosing which panel groups egui sees before vs. after the terminal's bottom panel each frame — whichever is declared first claims full height, the rest are inset to what's left, so the same four combinations fall out without separate layout math per option.

### Added (reload window)

- **Ctrl+Shift+R / File > Reload Window** restarts Forge IDE in-place — same PID, not a full quit-and-relaunch through the OS. Uses `exec` (Unix) to replace the running process image with a fresh invocation of the on-disk binary, so a rebuild since this process started takes effect immediately. Session state (open tabs, terminal directories) is saved first and restored on the way back up, and the workspace path is passed explicitly as a CLI argument so the same folder reopens regardless of the OS-level working directory. As a side effect, `forge-ide <path>` now also works standalone (`code .` equivalent) — previously any CLI argument was silently ignored.

### Added (settings discoverability)

- **Settings was only reachable via Ctrl+, with no visible entry point.** Added a gear icon pinned to the bottom of the activity bar (matching VS Code's placement) and a "Settings" item in the File menu, both opening the same settings panel Ctrl+, already did.

### Added (session persistence)

- **Forge IDE now remembers open tabs and terminal directories per workspace, and restores them on the next launch** — like VS Code. Saved to `<workspace>/.forge/session.json` on window close (already gitignored, personal runtime state, not shared config). This doesn't replay terminal scrollback/history — a restored terminal is a fresh shell in the same directory, same as VS Code's own terminal restore. Controlled by a new "Restore Tabs & Terminals on Startup" toggle in Settings (Ctrl+,), on by default.

### Fixed (terminal, missing cursor)

- **The terminal cursor could disappear entirely in TUIs like Claude Code.** DEC private-mode sequences (`ESC[?25h`/`ESC[?25l` — cursor show/hide) were completely unhandled; ink-based TUIs hide the real terminal cursor and draw their own in-content indicator, showing the real one only at an actual text-input point. Since we never tracked that state, our cursor stayed keyed only to focus/blink — whatever the last hide/show request was got silently ignored. Cursor visibility is now tracked and respected by both the local and SSH-remote terminal renderers.

### Fixed (terminal, misleading session-restore message)

- **New terminal tabs sometimes printed "Restored session: `<date>`" on startup even though nothing was restored.** `TERM_SESSION_ID` was inherited unchanged from Forge IDE's own process environment, so every spawned tab shared the same id as whatever terminal Forge IDE itself was launched from. macOS's built-in Terminal.app session-restore feature (`/etc/zshrc_Apple_Terminal`) keys its saved-on-exit restore script off that id — an unrelated shell elsewhere exiting with the same inherited id left behind a restore script that a new, unrelated tab here would then source. Each spawned shell now has `TERM_SESSION_ID` cleared so it's treated as the genuinely new session it is.

### Added (terminals survive Reload Window)

- **Local terminals (and whatever's running inside them — an active Claude Code session included) now survive Ctrl+Shift+R / Reload Window instead of being killed with the old process.** Root cause of the old behavior: `exec()` replaces Forge IDE's own process image, and the kernel handles that by closing Forge IDE's own file descriptors marked close-on-exec — which included the PTY master fd, whose closure sends `SIGHUP` to the shell attached to it (and anything running inside it). Terminals are now backed by a small local daemon (`forge-server --listen <socket>`, reusing the exact JSON-RPC PTY protocol already used for SSH remote terminals) that Forge IDE spawns once, detached into its own process group — a *different* process's file descriptors are untouched by Forge IDE's own exec, so the shells it owns are simply unaffected. On reload, Forge IDE reconnects to the same daemon and reattaches to the same running sessions by id (recorded in `.forge/session.json` and cross-checked against the daemon's live session list — a session that's genuinely gone falls back to a fresh shell, same as before). Falls back to owning the PTY directly (today's behavior, un-reload-survivable but fully functional) if the daemon can't be reached at all. Verified live end-to-end: opened a session, ran a command, fully disconnected the client (simulating what `exec` does), reconnected as a new client, and confirmed the same underlying shell process was still alive and responsive.

### Changed (session restore now opt-in)

- **Session restore defaults to off.** Remembering/restoring open tabs and terminals should be a deliberate choice, not a silent behavior change — the plan is to surface it (and similar choices) in a getting-started guide on first launch, matching VS Code's welcome tab, rather than picking a default silently (tracked in GAPS.md). Still available in Settings any time.

### Fixed (Reload Window ignored the opt-in session-restore setting)

- **Ctrl+Shift+R / Reload Window now always restores tabs and terminals, regardless of the "Restore Tabs & Terminals on Startup" setting.** That setting governs restoring across a genuine quit-and-relaunch later — an opt-in convenience the user may not want turned on. Reload Window is a different thing entirely: it's the *same session* continuing, just re-executing the on-disk binary in place, exactly like VS Code's own Reload Window always keeps your open editors. Previously both paths were gated on the same setting, so with it off (the new default) reload silently lost your tabs and terminals too. `reload_window` now saves session state unconditionally and passes a new `--reload` CLI flag to the freshly exec'd process, which restores that state unconditionally on startup — a true quit-and-relaunch (no `--reload` flag) still respects the setting as before.

### Added (build freshness indicator)

- **Settings now shows "Build: Xm ago"** — the currently running binary's file modification time. Reload Window restarts the process using whatever's already built on disk; it doesn't trigger a rebuild itself, so there was previously no way to actually confirm a reload picked up a fresh `cargo build` versus silently still running the old one.

### Fixed (terminal, copy/paste)

- **Cmd+V did nothing, and Cmd+C sent SIGINT to the running process instead of copying.** Two compounding bugs: (1) `key_to_pty` treated Cmd the same as Ctrl for terminal control codes, so Cmd+C mapped to the same byte as Ctrl+C (`\x03`, SIGINT) — Ctrl+C-means-SIGINT is a real, universal terminal convention, but it's tied to the physical Control key on every platform including macOS, not Cmd; (2) `egui::Event::Paste` (how egui surfaces the system paste shortcut, with the clipboard text already resolved) was never handled in the keyboard loop at all, so Cmd+V silently did nothing — only the right-click "Paste" menu item worked, since that reads the clipboard itself rather than relying on this event. Cmd+C now copies the terminal's text (matching the right-click "Copy" item — there's no partial mouse-selection yet, so it's the whole buffer) and Cmd+V now pastes correctly; Ctrl+C still correctly sends SIGINT.

### Added (terminal, cursor stays solid while typing)

- **The terminal cursor now stays solid (no blink) for 500ms after each keystroke**, so it's easy to keep track of while actively typing, resuming its normal blink rhythm once idle. Applies uniformly to any input (typed keys, paste, dragged file paths), not just literal keypresses.

### Added (terminal, background color / diff highlighting)

- **Claude Code's red/green highlight bands for removed/added lines never appeared — background colors had no effect in the terminal at all.** SGR 40-49 (and the bright 100-107 range) fell into a silent no-op catch-all in the ANSI parser; `Cell` had no field to even store a background color. Added background color as a proper part of cell state (256-color and truecolor forms included, mirroring the existing foreground handling), and taught the renderer to carry it through into a real highlighted region instead of just text color — including not trimming a highlighted-but-textless trailing run of a line, which would otherwise cut a highlight band short. Verified directly against the ANSI parser and the rendered output with a temporary unit test (now removed): a background sets and clears independent of foreground, and the color survives all the way into the actual `LayoutJob` section egui renders.

### Fixed (terminal, dim/faint text)

- **Hint text in TUIs like Claude Code (meant to render as grey) showed at full brightness instead.** SGR 2 (faint/decreased intensity) fell into a broad "skip unhandled attributes" catch-all in the ANSI parser — dim text was tracked as full-brightness the whole time, indistinguishable from normal text. Dim is now tracked as its own state (separate from the active color, since it needs to correctly combine with *whatever* color is set, not just whatever it happened to be when dim turned on) and halves the active color's brightness when rendering, with SGR 22 correctly resetting it. Verified with a temporary unit test directly against the ANSI parser (plain text unaffected, dim halves both the default and an explicit ANSI color, SGR 22 resets it) before removing the test, per this repo's no-permanent-test-infra convention.

### Fixed (macOS screenshot drag-and-drop — vendored winit patch)

- **Dragging the floating thumbnail after a Cmd+Shift+4 screenshot into the terminal didn't work, even though dragging a regular file from Finder did.** Root-caused in winit's own macOS source: its drag-and-drop handler only checks the legacy `NSFilenamesPboardType` pasteboard format, and rejects the drop outright if that's absent — Finder file drags still populate it for backward compatibility, but newer macOS system UI (the screenshot thumbnail included) only offers the modern `NSPasteboardTypeFileURL` type, which winit never checked at all. Vendored winit 0.30.13 into `vendor/winit-0.30.13` (patched via `[patch.crates-io]`) with a fallback: when the legacy type is absent, read each pasteboard item's file URL string and resolve it through `NSURL` instead of just giving up. Verified the patch compiles correctly against the actual resolved dependency versions (objc2-app-kit/objc2-foundation 0.2.2, not whatever a newer cached copy on disk happened to be) and that the logic is sound; the actual live drag-from-screenshot-thumbnail behavior needs a real test since it can't be exercised without a GUI.

### Fixed (terminal, blank after reattach)

- **A reattached terminal (after Reload Window) rendered as an empty black box until you typed something into it.** Working as designed in one sense — the daemon doesn't buffer output, so there's genuinely no scrollback to replay — but the shell also has no way of knowing a new client just connected, so it never reprints anything on its own either, leaving the fresh (empty) grid with nothing to show. Reattach now sends Ctrl+L immediately (`clear-screen`, bound by default in both bash/readline and zsh/zle), so the shell redraws its current prompt right away instead of sitting silently.

### Fixed (terminal, resize debounce)

- **Shrinking the terminal after growing it (or any drag-resize) could produce bursts of duplicate prompt lines partway through the gesture.** The previous fix debounced by frame count (commit once the same size is seen on 2 consecutive frames), but during an actual drag the mouse routinely moves slower than the frame rate — an intermediate size can render identically for several frames without the drag being over, and each of those was getting committed as a real resize (a real `SIGWINCH`, which the shell answers by reprinting its prompt on a fresh line — the same thing any terminal's shell does on a real resize, just usually invisible because the resize is debounced heavily enough that only one ever reaches the shell). Switched to a time-based debounce (400ms of held-steady size), which collapses the vast majority of drag gestures into a single resize at the end. Note this is a tuning tradeoff, not something with a hard "fully fixed" line — an unusually slow, deliberate drag can still pause long enough mid-gesture to leak through an intermediate resize, the same as it can in other terminals.

### Fixed (terminal, startup gap)

- **A freshly opened terminal showed a large empty gap above the prompt instead of the prompt sitting at the top.** The viewport grows from its small initial spawn size up to the real panel size within the first couple of frames; growing a viewport is supposed to reveal more scrollback history above the existing content where history exists, but a brand-new terminal has none — the code was unconditionally inserting the new rows at the top anyway (falling back to blank rows once scrollback ran out), which shoved the prompt down the screen instead of leaving it anchored at the top with the new blank space below it, like a real terminal does.

### Fixed (terminal, spurious resize on startup)

- **A freshly opened terminal could show several duplicate empty prompt lines with nothing typed.** Introduced by the previous fix: the panel's available width/height can wobble by a pixel or two for the first few frames while the surrounding layout (sidebar badges, file tree population, etc.) settles. Since resize now also tracks columns (not just rows), each of those transient blips fired a real PTY resize — a real `SIGWINCH`, which a shell sitting at an idle prompt answers by redrawing it. A resize is now only committed once the same size is observed on two consecutive frames, which absorbs both single-frame blips and longer multi-frame settling without adding any perceptible delay to an actual user-driven resize.

### Fixed (terminal, resize corruption)

- **Resizing the terminal while a heavy TUI (Claude Code) was running left stale duplicate content behind.** The terminal grid had no concept of a fixed-size viewport — it was one ever-growing list of rows, hardcoded to 120 columns regardless of the actual panel or PTY size. Real terminals (and what ink-based TUIs like Claude Code assume) have a genuine fixed viewport: "erase to end of screen" and cursor-relative redraws are relative to *that*, not the entire scroll history. Rewrote the grid as a proper fixed-size viewport with a separate scrollback (lines only move into scrollback when they actually scroll off the top), and wired the *actual* rendered panel size — both rows and columns, not just rows — into the grid and the PTY on every resize, matching how a real terminal reconciles a resize (pulling lines back from scrollback when growing, pushing the top rows into scrollback when shrinking).

### Fixed (terminal, rendering corruption)

- **Terminal output got garbled/overlapping text for heavy-TUI tools like Claude Code.** The PTY reader read raw bytes in fixed 4096-byte chunks and decoded each chunk independently via `String::from_utf8_lossy`. A multi-byte UTF-8 character (box-drawing lines, spinner glyphs, bullets — all over Claude Code's UI) landing across a chunk boundary got mangled into replacement characters on *both* sides of the split, throwing off the terminal grid's column tracking for everything printed afterward — which is what produced the stray/overlapping characters and tofu boxes. Incomplete trailing sequences are now held back and prepended to the next read instead of being decoded prematurely.

### Fixed (renderer)

- **Possible GPU crash (`VK_ERROR_OUT_OF_DEVICE_MEMORY` / lost device / `GPU Address Fault`) from texture updates.** `EguiPass` never tracked each uploaded texture's actual allocated dimensions, so a partial texture "patch" (egui's mechanism for adding new glyphs to the font atlas, or similar incremental updates) was issued with whatever offset/size the delta reported, with no check that it actually fit inside the image that was really allocated on the GPU. A patch landing outside those bounds is a `vkCmdCopyBufferToImage` writing past the image's real memory — exactly the shape of the reported page fault. Out-of-bounds patches are now detected and dropped (with a logged warning) instead of being issued.

### Fixed (terminal)

- **Typing in the terminal leaked into IDE keyboard shortcuts.** Global shortcuts (Ctrl+N, Ctrl+P, Ctrl+F, Ctrl+K, F9, F5, …) were checked unconditionally every frame regardless of what had focus, so shell/readline chords — Ctrl+P/Ctrl+N for history, Ctrl+F, etc. — fired the terminal's own PTY input *and* the IDE's Quick Open/New File/breakpoint-toggle/etc. behind it at the same time. Global shortcuts are now suppressed while a terminal (local or SSH remote) has keyboard focus.

### Fixed (editor)

- **Every open tab shared the same scroll position.** The editor's scroll area used a fixed ID regardless of which file was open, so egui persisted one shared scroll offset for all tabs — scrolling in one file moved every other open file to the same line. Now keyed per-buffer (by path, or tab index for unsaved buffers), so each tab keeps its own scroll position independently.

### Fixed (performance)

- **Editing large files (this repo's `app.rs` included) was slow.** The editor re-ran syntax highlighting — a full tokenizing pass over the *entire* file — on every single frame, not just on edits, because egui's `TextEdit` layouter runs continuously. Caching just the highlighted `LayoutJob` wasn't enough: a "hit" still meant cloning the whole file's text and every color span, then handing that to egui's font system to re-hash and re-shape from scratch, every frame. Now the fully-shaped, render-ready output (the `Galley`) is cached directly — a hit is just a cheap pointer clone, with zero tokenizing, hashing, or text shaping — and only actually recomputes when the text, extension, font size, search matches, or theme have changed since the last frame.

### Added (follow-up 3)

- **The welcome-screen anvil watermark heats up as the Forge Agent works.** Cold and barely visible at rest, it warms from dim gray through red, orange, and pale yellow-white — each tool call is a hammer strike that jumps the heat up, and between strikes it only cools a little while the agent is still working (so it's obviously still hot, just waiting on the next tool call), cooling fully once the turn ends.
- **Forge Agent panel: no more duplicate conversations.** Clicking "+" now reuses an already-open, untouched new tab instead of spawning another blank one (and another `forge-agent` process) every click. Opening a saved conversation that's already open in a tab switches to it instead of opening a second copy.

### Fixed (editor audit)

- **Trailing newline was stripped on every save.** `Buffer` parsed file content with `str::lines()`, which silently discards whether the file ended in `\n` — every save then wrote the content back without one. This fought any formatter (rustfmt included) that enforces a trailing newline, on both local and SSH-remote saves. `Buffer` now remembers whether the file had one when loaded and restores it on save.
- **Redo didn't exist.** Only `Ctrl+Z` (undo) was wired to anything — there was no redo stack, method, or keybinding at all. Added a proper redo stack (cleared on a fresh edit, per standard undo/redo semantics) and wired both common conventions: `Ctrl+Y` and `Ctrl+Shift+Z`.
- **No syntax highlighting for JSON, YAML, Shell, or Markdown** — the config/script languages every project has, previously rendered as flat text (though strings/numbers/brackets already had baseline coloring from the tokenizer's generic passes). Added keyword/comment/literal recognition for all four, including shell `$VAR`/`${VAR}` and single-quoted strings, and Markdown headings + inline/fenced code.

### Added (editor audit)

- **File watcher for external changes.** `git checkout`, a pull/rebase, or another process editing a file no longer leaves an open buffer silently stale — it reloads automatically (or warns instead of overwriting, if the buffer has unsaved edits), the same policy already used for the agent's own live-reload. Watches the workspace recursively via `notify`, ignoring `.git`/`target`/`node_modules`/`.forge`.
- **Multiple concurrent terminal instances**, matching VS Code: a tab strip above the terminal (switch, close, "+" to open another). Each terminal keeps running in the directory it was opened in, even if you later open a different folder — only new terminals pick up the new cwd. "Open in Integrated Terminal" from the file tree now opens a new terminal tab instead of replacing whatever was already running.
